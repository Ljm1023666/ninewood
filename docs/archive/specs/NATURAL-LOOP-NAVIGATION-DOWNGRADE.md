# 平台内置功能回归自然回体系

## 任务目标

以 `/loops` 为唯一运行状态中心，重新梳理 Ninewood 当前平台内置功能：

- 自动触发、自动执行、自动验证、自动产出结果的能力，建模为**天回**。
- 需要用户与九木界面交互的能力，保留为**地回**。
- 需要用户与其他用户协作的能力，保留为**人回**。

不要把“页面”机械等同于“回”。页面可以继续存在，但页面背后的自动能力必须进入自然回体系。

## 导航目标

左侧导航最终收敛为核心入口：

- 发现
- 卡池
- 发布
- 圈子
- 回
- 消息
- 我的
- 帮助

以下入口需要从左侧导航移除、降级或并入合适的核心入口：

- 监控
- 税务可视化
- 自动化任务
- 标签统计
- 推送设置
- 自动认证检查
- 订单超时与自动结算
- 福利自动发放
- 路径索引维护

不能简单删除这些页面或功能。页面中的人工操作必须保留在合适位置，自动部分进入天回。

## 功能拆分要求

### 1. 监控

将当前监控能力拆分为：

天回：

- 系统健康监控
- 接口异常检测
- 数据质量监控
- 服务可用性检测
- 异常告警

后台人工工具：

- 创建标签
- 标签管理
- 管理员配置
- 人工处理异常

监控天回必须能在 `/loops` 查看运行状态；管理员工具不应被误认为普通用户的天回。

### 2. 自动化任务

自动化任务是优先级最高的天回候选：

> 自然语言描述任务 → AI 构建执行流程 → 自动运行 → 验证结果

任务页面只保留：

- 新建任务
- 查看运行状态
- 查看执行日志
- 查看结果
- 暂停/恢复任务

任务的实际运行实例必须进入 `/loops`。

### 3. 标签统计与自动分类

以下能力建模为天回：

- 自动提取标签
- 自动统计标签热度
- 自动计算完成数量
- 自动更新分类覆盖率
- 自动发现分类缺口

人工编辑标签仍然属于地回或后台管理，不要全部迁移为天回。

### 4. 推送与提醒

`/push-settings` 是配置页面，不要把配置页面本身当成天回；其背后的自动能力应建模为天回：

- 需求匹配
- 条件筛选
- 定时推送
- 超时提醒
- 订单状态提醒
- 回运行异常提醒

配置入口可以放入“我的”或“回”的设置区域。

### 5. 税务

当前税务可视化页面是用户主动选择主体、税种并点击计算，暂时属于地回。

以下能力可以建模为天回：

- 根据收入和交易自动汇总
- 自动计算预估税额
- 自动比较税务方案
- 自动提醒申报期限
- 自动生成税务报告

不要直接删除当前手动税务计算能力，也不要把手动页面错误标记成天回。

### 6. 路径检索

当前路径检索页面属于地回，因为用户需要输入条件、调整筛选和查看结果。

以下后台能力属于天回：

- 自动维护路径索引
- 自动更新路径覆盖率
- 自动推荐匹配路径
- 自动检测路径失效
- 自动发现需求卡与服务卡的新匹配

### 7. 认证

认证申请和材料提交需要用户参与，属于人回/地回。

以下能力可以建模为天回：

- 自动检查材料完整性
- 自动检测证书过期
- 自动验证外部证书状态
- 自动更新认证状态
- 自动发现认证异常

### 8. 订单、交易与钱包

订单、交易和钱包页面本身不能整体删除，因为用户需要查看和人工处理。

以下自动能力应进入天回：

- 自动检测订单超时
- 自动更新订单状态
- 自动结算
- 自动分账
- 自动退款
- 自动对账
- 自动检测争议风险

页面保留人工查看、确认、申诉和处理入口。

### 9. 福利与激励

以下能力可以建模为天回：

- 自动判断完成条件
- 自动发放奖励
- 自动计算积分
- 自动检测资格
- 自动结算激励

用户主动领取、确认或参与的部分仍然属于人回或地回。

### 10. 圈子运营

圈子交流本身是人回。

以下后台能力可以建模为天回：

- 自动推荐圈子
- 自动检测圈子活跃度
- 自动识别垃圾内容
- 自动更新圈子健康状态
- 自动提醒圈主处理异常

## 技术要求

1. 优先复用现有：
   - `LoopDefinition`
   - `LoopOffering`
   - `LoopRun`
   - `LoopEvent`
2. 必要时新增清晰的数据模型、API 和前端状态。
3. 所有自动能力必须有明确的：
   - 触发条件
   - 执行过程
   - 验证方式
   - 成功结果
   - 失败结果
4. 自动能力必须能在 `/loops` 查看：
   - 所属分区：天回/地回/人回
   - 当前状态
   - 触发方式
   - 当前阶段
   - 成功次数
   - 失败次数
   - 最近运行时间
   - 最近结果
   - 错误信息
5. 仅调整展示分区不能改变原有业务类型或业务状态。
6. 保留需求卡、服务卡、订单、消息和自然回主链路。
7. 不得通过删除页面、删除路由或删除接口来伪造完成。
8. 需要区分：
   - 普通用户能力
   - 管理员后台能力
   - 系统自动运行能力
9. 不新增移动端适配、触摸事件、PWA 或移动缓存功能。

## 建议实施顺序

### Phase A：能力盘点

- 列出当前所有导航入口、页面、API 和后台任务。
- 为每个功能标注：天回、地回、人回、后台管理或混合。
- 明确页面与自动运行能力的拆分关系。

### Phase B：天回建模

- 为监控、自动任务、推送、标签统计等能力建立 LoopDefinition/LoopOffering。
- 为已有自动任务补齐 LoopRun 和 LoopEvent。
- 补齐成功、失败、超时和重试状态。

### Phase C：运行中心接入

- 在 `/loops` 增加天回能力展示。
- 支持按能力、状态、最近运行时间和成功率排序。
- 从天回卡片进入详情或配置页面。

### Phase D：导航收敛

- 移除重复的独立导航入口。
- 将配置页面放入“我的”或对应天回详情。
- 保留必要的管理员入口，但不要混入普通用户主导航。

### Phase E：验证

- 验证自动监控可以生成并更新天回运行实例。
- 验证自动任务可以在 `/loops` 显示运行状态和结果。
- 验证税务手动计算仍可用。
- 验证订单、认证、福利等人工流程没有被删除。
- 验证导航中不再出现可以由“回”统一承载的重复入口。

## 验收标准

完成后必须提供：

1. 功能分类表：每个原页面/能力对应天回、地回、人回或后台管理。
2. 变更文件清单。
3. 导航变更说明。
4. 天回模型与 API 说明。
5. `/loops` 验收路径。
6. 数据库迁移说明。
7. 已知限制。
8. 测试结果。

必须运行并报告：

- 数据库迁移检查
- 后端 typecheck
- 前端 typecheck
- 相关 lint
- 相关单元测试
- 关键页面和 API 的最小烟囱验证

完成后不要提交空泛的“已完成”，必须说明哪些功能真正接入了天回，哪些功能只完成了分类或导航调整，哪些仍然需要后续实现。
