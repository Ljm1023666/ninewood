# 需求卡与服务卡统一扩展 ADR

## 状态

已接受，第一版实现。

## 决策

- `Demand` 继续表示需求卡，保持现有发布和申请/订单合约。
- 新增 `ServiceCard` 表示公开服务声明，任何用户都可以创建、编辑、发布和下架自己的卡片。
- `ServiceCardClaim` 只保存发布者声明；`isHighlighted` 由平台根据经验事实更新，不能由请求体直接伪造。
- `ServiceCardEvidence` 只保存按业务词聚合后的完成数量、成功数量、成功率和最近完成时间，不保存客户身份、订单号、需求正文或私聊内容。
- `CardAttachment` 保存消息中的 `DEMAND`/`SERVICE_CARD` 类型、关联 ID 和发送时快照。卡片后续编辑、下架或删除不改变历史消息展示。
- 统一检索接口通过 `resultType` 区分需求卡和服务卡；身份偏好只改变排序，不改变查看权限。

## 一致性与权限

- 服务卡写操作在路由边界校验字段，并由服务层再次校验所有权。
- 卡片附件发送时必须证明发送者拥有该卡片；接收方只需要拥有会话关系即可查看公开快照。
- 经验聚合只消费 `OrderStatus.COMPLETED` 的订单；取消、退款和争议订单不计入成功事实。
- 聚合失败不阻断订单结算，采用影子更新并记录错误日志，后续可由重算任务修复。

## 迁移策略

1. 先部署 `20260712190000_add_service_cards`，创建服务卡、声明、经验和附件表及索引。
2. 不迁移旧 `Demand` 数据为服务卡，避免改变需求卡所有权和生命周期语义。
3. 新代码先以服务卡独立 API 提供能力；旧 `/demands/create` 保留，`/publish` 作为统一入口。
4. 订单完成时增量重算服务者相关服务卡；后续可增加全量重算命令修复历史数据。
5. 如需回滚，保留需求卡和消息主表，仅回滚新表与服务卡路由，不删除历史需求或消息。
